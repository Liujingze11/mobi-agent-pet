## 重复会话原因

用户日志在 14:32:03 显示恢复原始 Claude 会话 ID，14:32:43 的 Stop 事件以编码 ID 新建会话。两者对应同一个会话与进程。恢复路径此前将原始 ID 直接作为 Map 键，HTTP 路径则使用 `s1` 编码键，因而生成两张卡片。

## 通用会话身份与跨系统场景

会话登记按来源配置 `profileId` 与原始会话 ID 生成同一个内部键。实时 HTTP 状态、审批和 Codex 日志入口已经沿用这套规则；此次修复让 Claude 启动恢复也遵守它。ID 生成不依赖操作系统、目录格式或进程号。同一进程可以运行多个真实会话，目录和进程号不用于将它们强行合并。

新增 12 个场景测试：Linux / macOS / Windows 参数下分别验证恢复先到、真实 HTTP Hook 先到、同一进程和目录中的两段真实会话，以及本地和两个远程配置使用同一个原始会话 ID。测试调用真实的租约持久化/读取、恢复逻辑、HTTP 状态处理和状态快照，只替换系统进程探测及日志回调。恢复先到与 Hook 先到最终都只有一条会话；不同会话或远程配置保持独立。

这 12 个新增场景全部通过。通过内存加载临时退回原始 ID 登记的旧行为后，12 个场景全部按预期失败，证明能够捕获原问题；没有改写生产源码来进行该验证。状态、HTTP 入口、日志入口、身份键、恢复租约相关测试再次通过。

以上为在 Linux 上模拟三个系统参数的自动化验证，并非三个操作系统的实机验证。它覆盖已定位的身份不一致问题，不代表任何类型的重复显示都能仅靠这一项修复。
